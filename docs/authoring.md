# Authoring C#/WinRT Components

## Overview

CsWinRT 3.0 supports authoring Windows Runtime components in C#. Set `CsWinRTComponent` to `true` to generate a `.winmd` describing the component's Windows Runtime API. Other Windows Runtime languages, such as C++/WinRT, consume that metadata; ordinary managed callers can reference the component's managed implementation directly.

## Creating a component

Create an SDK-style C# class library and reference the `Microsoft.Windows.CsWinRT` 3.0 package.

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <TargetFramework>net10.0-windows10.0.26100.1</TargetFramework>
    <WindowsSdkPackageVersion>10.0.26100.85-preview</WindowsSdkPackageVersion>
    <CsWinRTComponent>true</CsWinRTComponent>
    <DisableRuntimeMarshalling>true</DisableRuntimeMarshalling>
    <Nullable>enable</Nullable>
  </PropertyGroup>

  <ItemGroup>
    <PackageReference Include="Microsoft.Windows.CsWinRT" Version="$(CsWinRTVersion)" />
  </ItemGroup>
</Project>
```

Replace `$(CsWinRTVersion)` with the CsWinRT 3.0 package version you are using.

For a project named `MyComponent`, add a runtime class:

```csharp
using Windows.Foundation.Metadata;

namespace MyComponent;

[Version(1)]
public sealed class Greeter
{
    public string Greet(string name) => $"Hello, {name}!";
}
```

Build from a compatible Visual Studio developer command prompt:

```powershell
msbuild MyComponent.csproj /restore /p:Configuration=Release
```

Managed components can build as AnyCPU, the default for an SDK-style class library. Native hosting DLLs must match the consumer's architecture, even when the managed component is AnyCPU.

### What the build generates

CsWinRT generates the component's WinMD, projection code, and activation factories, while the authoring analyzers validate its exported API. After C# compilation, `cswinrtwinmdgen.exe` reads the compiled component and writes its `.winmd`, which is copied to the component's output directory. The metadata therefore includes eligible declarations from generated source as well as handwritten code.

When an application or native-hosting build needs the implementation, CsWinRT generates `WinRT.Component.dll` for component ABI dispatch, the required projection assemblies, and the application-wide `WinRT.Interop.dll` marshalling sidecar. With Native AOT, this implementation code is compiled into the native output. These assemblies are generated by build tools after C# compilation.

Do not enable `CsWinRTGenerateReferenceProjection` on the implementation project: a component contains executable managed code. A separate projection library can use reference-projection mode to distribute a projection of the component's `.winmd`.

## Designing the exported API

Not all C# types and language features can be exposed through Windows Runtime. Design the exported surface around Windows Runtime types, and keep managed-only helpers internal or explicitly exclude them.

- Exported types must be public, top-level, and declared in a namespace matching the assembly name or one of its child namespaces. Namespace prefixes must not differ only by casing.
- Newly authored runtime classes must be sealed unless static.
- Authored generic types, generic methods, operators, arbitrary managed base classes, and unsupported managed signature types cannot be exported. Supported custom mappings include types such as `DateTimeOffset`, `TimeSpan`, and the mapped .NET collection interfaces.
- An exported property needs a public getter. Structs need public instance fields with supported Windows Runtime field types; non-public instance fields and constant fields are diagnosed.
- Constructors must have distinct input-parameter counts. For same-name method overloads with the same input-parameter count, select exactly one `[DefaultOverload]`; `out` parameters do not count as inputs.
- Use Windows Runtime async interfaces for exported asynchronous APIs rather than exposing `Task` directly.

Declare API versioning with `[Version]` or `[ContractVersion]`. The authoring analyzers also check API-contract enums, contract-version consistency, and mixed versioning attributes. See [attribute projections](attribute-projections.md) for versioning, deprecation, and experimental metadata. In particular, `[Obsolete]` alone does not communicate deprecation to other Windows Runtime language projections.

### Array parameters

CsWinRT 3.0 derives the Windows Runtime array direction from the C# parameter shape:

| C# parameter | Windows Runtime convention |
| --- | --- |
| `ReadOnlySpan<T>` | Input array (`PassArray`) |
| `Span<T>` | Caller-allocated output array (`FillArray`) |
| `out T[]` | Callee-allocated output array (`ReceiveArray`) |

Pass spans by value. `ref T[]`, `in T[]`, by-reference spans, jagged arrays, and multidimensional arrays are not supported authoring conventions. The old array-direction-attribute guidance is not the model for these signatures.

### Excluding managed-only API from component metadata

Use `[WindowsRuntime.InteropServices.ExcludeFromWindowsMetadata]` on a public type or member to keep it available to managed callers without including it in the component's `.winmd` or generated projections:

```csharp
using WindowsRuntime.InteropServices;
using Windows.Foundation.Metadata;

namespace MyComponent;

[ExcludeFromWindowsMetadata]
public class ManagedHelper<T>;

[Version(1)]
public sealed class Widget
{
    public void Refresh() { }

    [ExcludeFromWindowsMetadata]
    public System.Threading.Tasks.Task RefreshAsync() => System.Threading.Tasks.Task.CompletedTask;
}
```

The attribute supports classes, structs, interfaces, enums, delegates, constructors, methods, whole properties/events, and enum values. Excluding a type also excludes its members, but does not automatically exclude derived types. Excluded constructors and static members do not contribute activation or statics interfaces. Generated declarations follow the same rules.

An exported class can derive from an excluded managed base class, whether abstract or concrete. Its WinMD base is `System.Object`; the actual managed inheritance is unchanged. Inherited members are not automatically added to the exported API: re-expose selected members with public forwarding methods or overrides on the derived class, or declare a retained Windows Runtime interface on the derived class whose implementation can be inherited from the base.

Interfaces inherited only through an explicitly excluded base are also omitted from the derived class's WinMD, for both Windows Runtime interfaces and custom-mapped interfaces such as `IDisposable` or `IList<T>`. To publish one, repeat it in the derived class's base list (`public sealed class Widget : ManagedBase, IDisposable`); inherited public implementations can satisfy it without duplicating their bodies. The redeclared contract includes its required base interfaces. This opt-out boundary applies only to explicitly excluded bases: ordinary abstract managed bases, such as `CollectionBase`, retain their existing custom-mapped interface behavior.

Exported signatures, struct fields, and retained base contracts cannot reference excluded types, including through arrays or generic arguments (`CSWINRT2049`, or `CSWINRTWINMDGEN0016` from the metadata tool). A class may implement an excluded interface without listing it in its WinMD. Other retained interface contracts still apply, and unmarked public implementations remain ordinary exported members unless explicitly excluded. A member required by a retained interface cannot be excluded independently, including members inherited by custom-mapped collection interfaces such as `IList<T>`; neither can an individual property/event accessor or an instance field defining an exported struct's layout (`CSWINRT2048` / `CSWINRTWINMDGEN0015`).

This is metadata shaping, not access control or a COM-marshalling opt-out. Supported interfaces inherited from an excluded base can still have native CCW vtables and be queried through `QueryInterface`, even when absent from the derived class's WinMD. `[WindowsRuntimeManagedOnlyType]` is a separate attribute with different marshalling semantics.

## Activation factories

For newly authored runtime classes, CsWinRT generates activation and statics interfaces from the exported constructors and static members. A class with no exported constructors or static members has no activation factory generated for that purpose. Excluding a constructor does not invent a replacement parameterless constructor.

### Adding interfaces to an activation factory

To add an interface that native callers can query on the factory, declare a public abstract extension class annotated with `[WindowsRuntimeActivationFactory]`, naming the authored runtime class. The generated factory derives from that class while still implementing the generated activation and statics interfaces:

```csharp
using System.Runtime.InteropServices;
using System.Runtime.InteropServices.Marshalling;
using WindowsRuntime.InteropServices;
using Windows.Foundation.Metadata;

namespace MyComponent;

[Version(1)]
public sealed class Widget;

[GeneratedComInterface]
[Guid("6E1D3C6B-2E5B-4C8A-9E4F-3A7B1F2C9D10")]
internal partial interface IWidgetFactoryInterop
{
    int GetMagicNumber();
}

[WindowsRuntimeActivationFactory(typeof(Widget))]
public abstract class WidgetFactoryExtensions : IWidgetFactoryInterop
{
    int IWidgetFactoryInterop.GetMagicNumber() => 42;
}
```

The extension class must be public, non-generic, and abstract, with a public or protected parameterless constructor and no abstract members. Its containing types, if any, must also be public. The generated factory is compiled into a separate assembly, so it must be able to derive from and construct the extension class. The extension class itself is not a runtime class and is not included in the component's `.winmd`.

Each runtime class can have at most one activation-factory extension. Invalid declarations are reported as `CSWINRT2023`, invalid runtime-class arguments as `CSWINRT2024`, and duplicate factories as `CSWINRT2025`. The extra COM interface has its own vtable, queried by IID; it does not append slots to an existing activation interface.

## Deployment models

### Managed hosting

A managed component runs on CoreCLR through `WinRT.Host.dll` and `WinRT.Host.Shim.dll`. The authoring targets generate `WinRT.Host.runtimeconfig.json` and arrange hosting assets for project-reference consumers and component packages. Native consumers also need the generated component/projection/interop assemblies and the component's managed dependencies.

For C++ project-reference consumption, install the `Microsoft.Windows.CsWinRT` package in the native project so its native build targets are imported. Those targets aggregate the referenced managed components and generate one compatible hosting bundle for the native application. Keep all the resulting runtime assets together; copying only the component DLL and WinMD is insufficient.

### Native AOT

Native AOT publishing requires the Windows C++ build tools. Configure the native shared-library settings:

```xml
<PropertyGroup Condition="'$(PublishAot)' == 'true'">
  <NativeLib>Shared</NativeLib>
  <SelfContained>true</SelfContained>
</PropertyGroup>
```

Then enable `PublishAot` when publishing for a concrete runtime identifier:

```powershell
msbuild MyComponent.csproj /restore /t:Publish /p:Configuration=Release /p:RuntimeIdentifier=win-x64 /p:PublishAot=true
```

The authoring source generator emits the native activation export when `PublishAot` is enabled. Deploy the published native `MyComponent.dll`, not the managed intermediate DLL with the same name. Native AOT components do not require `WinRT.Host.dll`, its shim, or a managed runtime configuration file. Their activation registration names the native component DLL directly.

Publishing and packing are different operations. `Pack` alone does not publish a Native AOT library or automatically turn a managed component package into a native, RID-specific distribution. Package the published native assets for each supported architecture together with the component metadata and any required resources.

## Packaging a component

For a managed component, use the SDK's `Pack` target:

```powershell
msbuild MyComponent.csproj /restore /t:Pack /p:Configuration=Release
```

The authoring targets contribute the component's WinMD under `lib\<tfm>\winmd`, component-specific `build` / `buildTransitive` targets, and managed-hosting assets when applicable. The normal SDK pack process includes the managed component assembly.

Reference-projection packages are a different kind of package: they contain compile-time reference projections, type-forwarding implementation assemblies, and the metadata needed to generate implementations in consuming applications. Do not package an application-specific `WinRT.Interop.dll` as a reusable projection implementation; it is generated for the consuming application's complete set of assemblies.

If a native component package uses a custom layout, its targets can contribute a `CsWinRTNativeComponent` item to the C++ consumer's build:

```xml
<ItemGroup>
  <CsWinRTNativeComponent Include="path\to\MyComponent.dll">
    <CsWinRTComponentTargetFramework>net10.0-windows10.0.26100.1</CsWinRTComponentTargetFramework>
    <CsWinRTComponentWindowsSdkPackageVersion>10.0.26100.85-preview</CsWinRTComponentWindowsSdkPackageVersion>
  </CsWinRTNativeComponent>
</ItemGroup>
```

Here the item points to the **managed** component implementation for the native-hosting aggregation step, not to a Native AOT DLL. Project references supply equivalent component metadata automatically. Component packages must also make their WinMD available to C++/WinRT.

## Consuming a component

### From C#

Reference the component project or managed component package from a compatible .NET application. Direct calls use the original managed classes and normally do not involve Windows Runtime activation:

```xml
<ItemGroup>
  <ProjectReference Include="..\MyComponent\MyComponent.csproj" />
</ItemGroup>
```

Use the managed build for direct managed references. A published Native AOT DLL is not a managed assembly that can replace it. When consuming through a Windows Runtime projection instead, reference a projection library for the component's WinMD; do not generate a competing definition of its types inside the component implementation project.

### From C++/WinRT

Add a project reference or a component package that supplies the `.winmd` to the C++/WinRT build. For managed hosting, also enable the native CsWinRT build integration described above. Initialize the Windows Runtime on the calling thread and use the generated projection:

```cpp
#include <iostream>
#include <winrt/base.h>
#include <winrt/MyComponent.h>

int main()
{
    winrt::init_apartment();
    winrt::MyComponent::Greeter greeter;
    std::wcout << greeter.Greet(L"World").c_str() << L'\n';
}
```

Generating the C++ headers is only the compile-time step. Activation must also resolve the runtime class to its implementation, either through application registration or an appropriate explicit activation path.

### Activation registration

For a packaged application, register activatable classes in `Package.appxmanifest`:

```xml
<Extensions>
  <Extension Category="windows.activatableClass.inProcessServer">
    <InProcessServer>
      <Path>WinRT.Host.dll</Path>
      <ActivatableClass ActivatableClassId="MyComponent.Greeter" ThreadingModel="both" />
    </InProcessServer>
  </Extension>
</Extensions>
```

For an unpackaged application, the equivalent application manifest registration is:

```xml
<?xml version="1.0" encoding="utf-8"?>
<assembly manifestVersion="1.0" xmlns="urn:schemas-microsoft-com:asm.v1">
  <assemblyIdentity version="1.0.0.0" name="MyNativeApp" />
  <file name="WinRT.Host.dll">
    <activatableClass name="MyComponent.Greeter"
                      threadingModel="both"
                      xmlns="urn:schemas-microsoft-com:winrt.v1" />
  </file>
</assembly>
```

These examples use managed hosting. For a Native AOT component, replace `WinRT.Host.dll` with the published native component DLL, such as `MyComponent.dll`. Register each class that is activated through this path, and embed or deploy the application manifest as required by the native application build.

### Windows App SDK and XAML

Components can implement Windows Runtime and XAML interfaces/classes using the compatible projections and generated implementation bases. Use Windows App SDK/WinUI projection packages built for the CsWinRT 3.0 model. For UWP XAML, set `CsWinRTUseWindowsUIXamlProjections=true` consistently in the component and consuming build.

XAML still has its own resource, metadata-provider, initialization, and thread-affinity requirements. If the XAML compiler generates a `XamlMetaDataProvider`, register that activatable class too and include the generated XAML type-info projection where the native application's metadata-provider setup requires it. Use the names from the generated WinMD and XAML output rather than assuming a namespace or provider name.

The [authoring component](../src/Tests/AuthoringTest) and [WinUI consumption tests](../src/Tests/AuthoringWinUITest) show repository configurations.

### Out-of-process activation

`CsWinRTComponent=true` produces component metadata and DLL activation infrastructure; it does not by itself create or register an out-of-process executable server. That requires a server host, the appropriate Windows activation registration, and a deployment model for that host.

## Diagnostics and troubleshooting

The source analyzers report authoring problems while editing and compiling. `CSWINRT2010`-`CSWINRT2022` cover metadata/versioning attributes and related usage, `CSWINRT2023`-`CSWINRT2027` cover activation factories, and `CSWINRT2028`-`CSWINRT2049` cover exported API shapes and component exclusions. The post-build WinMD tool reports `CSWINRTWINMDGEN` diagnostics, including validation that still runs when source analyzers are disabled.

| Symptom | Check |
| --- | --- |
| No component WinMD is produced | `CsWinRTComponent=true`, `CsWinRTEnabled` has not been disabled, the build is not a design-time build, and the post-build tool completed successfully |
| A public helper causes authoring errors | Make it internal or use `[ExcludeFromWindowsMetadata]`; excluded types must not leak into exported signatures |
| Class activation fails | The class has exported activation/statics, its name matches the WinMD and registration, and the registered DLL matches managed hosting versus Native AOT |
| A native client cannot load a managed component | Matching architecture, the installed .NET runtime, `WinRT.Host.runtimeconfig.json`, the hosting shim, and the complete generated hosting bundle |
| The wrong projection/runtime is used | The `.1` TFM revision, compatible SDK reference pack and CsWinRT package, and no mixed 2.x/3.0 projection dependencies |
| Native hosting references disagree | Align component TFMs, SDK package versions, and XAML mode; the native targets provide `CsWinRTComponentTargetFrameworkOverride` and related overrides when needed |
| A post-build generator fails | Read its diagnostic, inspect the generated response file, or set `CsWinRTGeneratorDebugReproDirectory` to capture a self-contained repro |
